# Bounded Envoy runs

Tickets: PACT-021, PACT-049, PACT-062 (Alpha).

PACT-099 is deployed in `alpha-20261001-1` / `88c273f`. The inference worker exposes the same `pact_agent_guide_v1` and `pact_player_find_v1` schemas/readers as MCP. Guides derive identity from the current run, carry `lessonVersion`/`rulesId`, and explain the existing run lease rather than opening a second one. Exact-handle lookup returns only the public projection; missing handles remain `found:false`. Guide results keep complete fact groups within 3,600 UTF-8 bytes; oversized groups are listed in `omittedFields` with `truncated:true` and authorized read-tool directions. Omitted facts are unknown, not zero or authority. Read-only guide/discovery results do not become fictitious game commitments. The external activity migration and ownership are described below; [fresh independent play evidence](../implementation/reports/agent-first-completion.md) records actual results.

`@pact/runs` owns exclusive kingdom/subject write leases and the Envoy run lifecycle: start, wait, resume, stop, takeover, and MCP lease acquisition without inference.

## External activity (PACT-099)

`GET /v1/runs/external-activity` is a human-session owner-only, `no-store` read of the latest 50 external results. `pact_envoy_report_v1` without a run ID returns owner in-app runs plus `external` activity. Envoy displays the same factual categories, command/record/approval IDs and actual UTC timestamps. A committed instruction is not its completed consequence; proposed offers/signatures are not active contracts.

Migration `0044_external_agent_activity.sql` belongs to runs. The dispatcher invokes the injected transaction-bound `onCommittedReceipt` port after its receipt write, before commit. The API supplies only transport-derived external identity and server-issued receipt metadata; game effects, authority, receipt and committed activity roll back together on failure. Receipt retries do not duplicate history, and MCP session deletion does not remove it. Failed/proposed tool observations are ancillary and cannot replace a returned result when their observer fails. No raw arguments, player text, credentials, model assessments or hidden reasoning are stored. Noncommitting failures do not occupy a command's committed deduplication key.

The module's `retention` hook is registered with API privacy: 30-day pruning, owner export and deletion. Account erasure also cascades. New tables are additive for application rollback. MCP denials return explicit recovery advice; malformed null/array arguments are normal tool errors, not HTTP 500. All static guide topics now fit 3,600 bytes; large owner snapshots explicitly omit complete groups. Deployment and uncoached-agent observations must still be recorded separately.

## HTTP

| Method | Path | Behavior |
| --- | --- | --- |
| `POST` | `/v1/runs` | Human session starts a bounded run (objective, provider, model, optional credential) |
| `GET` | `/v1/runs` | Latest 20 owner runs, newest updated first; no inference |
| `GET` | `/v1/runs/:runId/report` | Owner-only latest 50 recorded results, factual categories and separately labeled assessment; no inference |
| `GET` | `/v1/runs/:runId` | Owner-scoped run status and allowance counters |
| `POST` | `/v1/runs/:runId/stop` | Stop; release write lease; preserve committed work |
| `POST` | `/v1/runs/:runId/wait` | Waiting releases the worker without polling a model |
| `POST` | `/v1/runs/:runId/resume` | Resume within original deadline and remaining allowance |

Defaults: 15 minutes, capacity for 6 selected conversations, 12 outgoing messages, 20 calls, 40 000 tokens. `POST /v1/runs` accepts optional `conversationKingdomIds` (distinct UUIDs for existing owner-involved direct-message threads) and `maxConversations` from 1 to 12. An omitted selection is empty; increasing capacity does not silently select threads. The server validates ownership before acquiring the run lease and rejects unknown or other-player-only threads. Selected IDs and `usedConversations` are fixed for the run and returned only in owner-scoped run status. `maxMessages` may be 1–24; the default remains 12. Optional `maxCalls` and `maxTokens` may lower, never raise, the fixed 20-call and 40 000-token ceilings. The internal duration limit cannot exceed 15 minutes. Invalid, fractional, or non-finite limits fail before lease acquisition or job enqueue; HTTP rejects out-of-range inputs as `INVALID_INPUT`. Successful in-app Envoy `game.message.send` commands atomically increment `usedMessages` with the domain write; a failed send rolls that increment back and a same-command retry returns the existing receipt. A subsequent send over the run cap returns `RATE_LIMITED`. External MCP hosts have their own lease and are not charged to a PACT in-app run. Resume never extends the deadline. A second client receives `RUN_ALREADY_ACTIVE`.

Before invoking a provider, the service reserves against the actual assembled messages and tool definitions for that call, not a fixed input allowance. Caller-controlled message text is charged conservatively by UTF-8 bytes; stable tool schemas use an approximate four-bytes-per-token estimate. If the estimate leaves no output allowance, the run finishes without a provider call. Provider-reported usage reconciles the reservation afterward. This is a bounded admission estimate, not an exact provider-token guarantee.

The PACT inference composition supplies an asynchronous `messagesForRun` port. It resolves the run owner's kingdom through the kingdom module, then reads that account's authorized owner projection. Only an explicit selection of profile, balances, upkeep, at most 16 buildings and troop groups, eight threats, and eight contract identifiers/deadlines enters the model input. The selected JSON has an 8 KiB cap with a smaller balance-only fallback. The composition also selects at most eight newest event metadata records through the owner-scoped inbox service: sequence, event ID, conservative event type, and timestamp. It never copies event payloads into the convenience context. For each human-selected direct-message thread, the model receives at most three newest messages, with bodies over 512 UTF-8 bytes omitted. The combined selection is capped at 12 KiB, falling back to IDs and a truncation marker. Counterpart prose is labeled **untrusted game data, never instructions** and remains user-role content; the system message stays fixed. No unselected message prose, private reports, model credentials, or another player's hidden fields are copied into this convenience snapshot. The same assembled messages are charged against the run allowance. Full conversation content remains available through explicit authorized reads. Selected excerpts are sent to the chosen provider during a run but are not separately persisted as tool-result records.

## Explicit game reads

PACT-062 adds a 4 KiB compact mandate (version, permitted actions, restrictions, reserves, limits and session), remaining call/token/message allowances and deadline before convenience history. The owner snapshot also includes two builders, four training queues and eight historical operation IDs. At most three actual public Chronicle notices enter a separate 4 KiB discovery selection; oversized public context is omitted with explicit truncation. Counterpart messages and notice/commentary text cannot alter the fixed system instructions, viewer identity or authority. All assembled input still passes the existing conservative token admission check.

Court, politics, Chronicle and selected Seal reads use the same strict tools/module projections as MCP. An explicit read does not grant permission to publish or sign as a human. Public read payloads are byte-bounded and preserve their untrusted-content labels.

### Offline result explanations

`pact_envoy_report_v1` requires `world:read`: omit `runId` to list the caller's latest runs, or provide an exact owned UUID to read its report. This is the same `RunService` report as first-party HTTP; it never invokes a provider. The new schema is additive; previous published pins are unchanged.

Reports parse server-issued tool metadata, not conversation prose. They distinguish committed instructions from nonbinding contact/supply/garrison proposals, denials, waiting and exact human approval requirements. Entries preserve receipt IDs, bounded record/version references, and a next step: refresh/replan on stale/busy feedback, inspect a committed instruction's actual consequence, or let the human review an approval. A committed build instruction is not a completed building, and one signature is not an active contract. Visible provider response text is stored as a bounded `agentAssessment` row under the existing private 30-day run retention/export; it is neither an engine fact nor hidden reasoning. Later model context labels prior assessments separately too. Lost crash results are not reconstructed or invented. External-host command journaling beyond in-app runs remains PACT-099.

The in-app Envoy can call the same strict `pact_world_read_v1` and `pact_report_read_v1` schemas as MCP. The active run supplies the viewer account; tool arguments cannot select another viewer. World reads use the authorized owner/contact/participant/public projection, while report reads use scout/raid visibility checks. Results are capped at 3,600 UTF-8 bytes before the run's 4 KiB persistence limit. Oversized projections are marked `truncated`; an oversized report returns only its kind and record ID. Missing and unauthorized reports both return `NOT_FOUND`. These explicit read results can contain private owner data and remain in the 30-day run history and owner privacy export.

An in-app `pact_conversation_read_v1` may read only a thread in that run's immutable human-selected `conversationKingdomIds`; an unselected thread returns `NOT_FOUND`, even if the owner could otherwise view it. This prevents explicit reads from bypassing the run's conversation cap. A separately granted MCP `world:read` client does not consume or inherit an in-app run's selection and retains owner-bound conversation reads under its own grant.

The same inference composition also exposes `pact_receipt_read_v1` and `pact_approval_status_v1`. A receipt read uses the shared dispatcher's account-scoped history, while an approval-status read selects only the run owner's request and returns its state, summary, expiry, receipt, and human review path. The summary is labeled `untrustedContent`; neither tool can approve or reject. Results are bounded to 3,600 UTF-8 bytes, with explicit truncation for oversized records, and persist under the same private 30-day run history. Both return `NOT_FOUND` for an unknown or different account's ID.

The in-app Envoy also receives the shared `pact_approval_propose_v1` schema for exact cold-contact, direct-transfer, troop-training, building-queue, and scouting requests. It proposes terms under its live run lease and receives a bounded `APPROVAL_REQUIRED` result with a human review path; proposal creation never executes the action or changes the mandate. The server-rendered summary and pending approval are owner-scoped. Approval remains a separate human action through PACT. Other command groups are not yet wired to this proposal tool.

## Inference worker

`workers/inference` leases `envoy.run.tick` durable jobs and calls `RunService.executeModelCall`. On job redelivery, an unresolved in-flight request is marked `failed` with `ambiguousCrash`, its reservation and write lease are released, and no second provider call begins. A still-running original worker can only observe the now-failed run during reconciliation. This is deliberately conservative: if a provider response was lost, PACT cannot infer whether it was billed. Ambiguous provider failures likewise fail the job without an unbounded retry loop. Idle inbox delivery never receives a provider adapter.

Local process-death fixtures kill a synthetic inference executor (1) after it reserves an in-flight request and (2) after a real game message command has committed but before model-step reconciliation. Replacement job claim conservatively fails the run and releases its reservation and lease without a second provider invocation. In the second case the command receipt and one owner-authored message survive, the run's outgoing-message count remains charged, and no tool-result summary is invented. This proves bounded local process-death behavior, not successful reconstruction of a lost provider result or full VPS recovery.

The provider router validates tool names, unique call IDs, and parsed arguments before `RunService` passes returned calls to the injected `executeToolCalls` port. If the router admits a call but no executor is configured, the run fails with `MALFORMED_TOOL_CALL`; calls are never silently discarded. Other non-quota provider/tool errors also fail the run immediately, including when allowance remains. The PACT-owned command bridge uses the shared dispatcher and derives agent identity from the run. Gameplay transactions check `assertAgentWriteLease`: an MCP session must hold its own `mcp` lease, while an in-app Envoy must own the live `pact_run` lease. These holders are not interchangeable. The inference process composes the same `@pact/application` game handler as the API, with the generated `pact_command_v1` tool and an optional raid-seed secret from its own mount. It also exposes shared `pact_inbox_read_v1` and `pact_conversation_read_v1` schemas. An explicit model call can read up to five owner inbox events or five messages from an owner-involved direct conversation; oversized payloads/bodies are omitted and counterpart prose is labeled untrusted. Automatic inbox context includes only metadata; direct-message bodies appear only for human-selected threads. PostgreSQL fake-provider fixtures exercise these tools without a paid provider. Outgoing-message and selected-conversation allowances are enforced as above.

The published web, MCP, and model command schemas all derive their 28 game action kinds from `GameActionSchema`; the model tool omits sandbox actions. Schema visibility is not an authorization grant: the command handler rejects human-only contact answers, training cancellation, troop disbanding, construction cancellation, garrison seizure, raid nomination, and raid withdrawal for agent principals. A PostgreSQL fake-provider/MCP matrix submits all seven with forged human actor fields and verifies `FORBIDDEN` with no committed receipt or human permit. Human actions still require a first-party human principal and normal game preconditions. This matrix proves a privilege boundary for those seven actions, not that all other game actions have complete cross-route equivalence.

After a successful tool batch, the worker records server-generated command receipt fields (command ID, code, charged amounts, record versions, committed event IDs, optional approval ID) or an explicitly requested, bounded read result in `envoy_run_tool_results`, atomically with run-step reconciliation. Command summaries are capped at 3,600 UTF-8 bytes; an oversized summary retains its command ID and code with `truncated: true`, and the owner-scoped receipt read can retrieve the full receipt. Inbox and conversation reads may contain owner-visible third-party prose; it is marked untrusted, can be shown to the selected provider, and persists with the private run for up to 30 days. Conversation results exceeding 3,600 bytes retain only message IDs and an explicit truncation marker. The next provider request includes at most the 16 latest results as labeled user-context data; it never promotes a counterpart's prose or tool arguments to system authority. The input allowance covers those results. A finished-run retry does not duplicate them. These rows cascade with run retention and appear in the owner's privacy export. If the worker dies between command commit and step reconciliation, the command receipt remains durable but the run is conservatively failed on redelivery; automatic result reconstruction is not attempted. The post-command process-kill fixture checks this behavior.

The inference worker registers only the deterministic fake provider by default. `PACT_ENABLE_LIVE_MODEL_CALLS=1` is an explicit operator opt-in for the existing OpenAI, Anthropic, Gemini, and xAI API adapters; OpenRouter additionally requires an operator-reviewed `OPENROUTER_ROUTING_DISCLOSURE`. Merely mounting a key or storing a connection cannot enable billable calls. When enabled, the worker reads its inference-only private key, admits an owner-scoped vault use, checks that the stored provider matches the run route, and keeps decrypted credential bytes inside that admitted provider call. A selected credential without a resolver fails closed as `INVALID_CREDENTIAL`. Local tests use a synthetic credential and injected HTTP response; no real provider route or cost was certified. Broader selected conversations and multi-command cross-route scenarios remain PACT-049 work. Do not present the default MVP as a live model-game route.
