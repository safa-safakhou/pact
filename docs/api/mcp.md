# MCP transport

`run.open` is an account-bound state-changing tool (`readOnlyHint: false`, scope `game:act`) with non-destructive, closed-world annotations. It reserves or renews one expiring session; it performs no game action, resource expenditure, inference or authority expansion. Renewal changes expiry, so its idempotence hint remains false. General game-write labels are unchanged. Host prompting policy is separate from these annotations and PACT authorization; an inherited low-risk-only policy does not guarantee autonomous writes. See [lease metadata and host permission evidence](../implementation/reports/mcp-lease-metadata-20261011.md).

Tickets: PACT-017, PACT-049; PACT-099 in progress.

`POST /mcp` and `GET /mcp` are the single Streamable HTTP surface. Clients authenticate with an MCP-audience Bearer access token from `@pact/oauth`. Origin must match `PACT_ORIGIN`. Supported protocol versions are `2025-11-25` and `2025-06-18`; unknown versions fail with `UNSUPPORTED_PROTOCOL`.

For a private Codex playtest, the browser OAuth authorization page accepts DCR-registered MCP clients, displays the client and requested scopes, and requires a human PACT sign-in before issuing a PKCE-bound code. Invalid redirect, resource, audience, or scope requests fail before a page is shown. An authorization code is bound to the registering client; another client cannot exchange it. Unauthenticated MCP requests advertise the protected-resource metadata in `WWW-Authenticate`. See [Codex playtest](../operations/codex-playtest.md) for the operator sequence. This does not certify a consumer host or make a pasted bearer token harmless.

## Sessions

`initialize` creates an `mcp_sessions` row and returns `Mcp-Session-Id`. Later `tools/list` / `tools/call` and `GET /mcp` streams require that session and bind it to the authenticated account. Another account cannot resume the session.
The `notifications/initialized` POST responds with empty HTTP 202, as required by Streamable HTTP clients; returning a JSON object here breaks Codex startup. Valid Bearer grants can initialize without invoking human-only approval checks.
Expected `tools/call` denials (for example `INSUFFICIENT_STOCK` or `INVALID_REQUEST`) return HTTP 200 with an MCP `isError: true` tool result containing only the error code. This preserves the session and write lease for the agent's next move. Invalid or missing authentication still uses HTTP 401, and a missing MCP session still uses its transport error.

## Tools

`pact_player_find_v1` resolves an exact public handle case-insensitively with `{handle:"known_player"}`; no UUID, caller account or viewer selector is needed. It requires `world:read`, never a write lease. Success returns `{found:true, kingdom:<public projection>, untrustedContent:true}`; an unknown/closing/retired identity returns `{found:false, kingdom:null, untrustedContent:true}` without inventing a player. Even an owner looking up their own handle gets no private state. Equivalent public HTTP read: `GET /v1/people/:handle`. See [public player discovery](../architecture/world-views.md). Real opportunities can now be discovered with `pact_chronicle_read_v1` notices and `pact_court_read_v1` rosters; this does not enumerate all accounts or automatically accept contact. Alpha handles remain fixed; full rename/history work is postponed. These features are local until the matching release is deployed.

`pact_profile_v1` is an authenticated, read-only `world:read` profile tool. It accepts only `{}` and returns a stable opaque account ID derived from the validated OAuth grant, plus a display-only kingdom-handle nickname when founded. Its `_meta["openai/profile"]: true` marker and `outputSchema` let compatible hosts distinguish connected accounts. The ID does not change with a token refresh, new session, or handle rename. It does not select another account, grant game authority, or list other players.

`world:read` first lists `pact_agent_guide_v1`. Call it with `{}` to enter the game without knowing a kingdom UUID: the server derives the owner from the OAuth grant and returns a compact owner state (whole-unit floors alongside exact marked balances), accepted contacts, pending contact requests, open supply offers, active contracts, mandate action names, and safe next steps. It omits private message bodies and contact-request prose; names/handles remain untrusted player data. It does not open a lease, alter state, or fabricate public opportunities. Optional `{topic:"development"|"diplomacy"|"military"|"authority"}` returns versioned lessons and typed action examples. `lessonVersion` identifies the lesson revision separately from authoritative `rulesId`. An unfounded account gets a truthful human-activation instruction. The shared `@pact/application` reader serves both MCP and the inference worker; the transport neither queries kingdom tables nor grants permission. Military includes catalog-backed garrison prerequisites and raid provisions/lock timing. Authority explains busy/stale/invalid recovery, exact human handoff and reconciliation using the original command ID. External lessons say to open the session-bound lease; in-app lessons correctly describe the existing bounded run instead. See [in-app result bounds](runs.md). Empty discovery results are not fabricated players.

`world:read` grants list `pact_world_read_v1`, which accepts `targetKingdomId` and an optional 1–60-minute forecast horizon. It returns the same owner/contact/participant/public projection as `GET /v1/world/kingdoms/:kingdomId`; the authenticated account, never tool prose, determines visibility. `game:act` grants list `run.open`, the sandbox tools, and `pact_command_v1`. `run.open` obtains one 15-minute write lease bound to the authenticated MCP session; it starts no model inference and a second active holder gets `RUN_ALREADY_ACTIVE`. A read-only grant cannot call write tools even by naming one directly, and the shared dispatcher rechecks the scope. `pact_command_v1` accepts social, troop, construction, supply, scouting, garrison, and raid actions in the shared envelope alongside sandbox actions. Gameplay writes check the exact live session lease transactionally; contact answer, training/building cancellation, disband, garrison seizure, raid nomination, and raid withdrawal are human-only. Agent cold-contact requests require the current mandate action `contact.request`, sufficient Silver allowance for the two-Silver fee, and an optional matching `mandateVersion`; transfer/training/construction/scouting/signature/raid contribution and contract-breaking actions likewise require mandate authority. No model-provider or consumer-chat certification is claimed.

`world:read` also grants `pact_report_read_v1` with `{kind, recordId}`. Kinds are `scout`, `raid_participant`, and `raid_public`; the last is a resolved or canceled raid's redacted public report. Scout reports require the originating kingdom or an explicit share. Private raid reports require the target or a committed contributor. Missing and unauthorized reports both return a not-found error. The equivalent HTTP endpoint is `GET /v1/reports/:kind/:recordId`; it accepts a human session or a Bearer grant with `world:read`, derives the viewer from that credential, validates the UUID, returns `Cache-Control: no-store`, and never accepts a viewer in the request. A development API without the raid-seed key can read scout reports but returns not-found for raid reports until the shared key is configured.

`world:read` also grants `pact_inbox_read_v1` with optional decimal `cursor` and `limit` (1–5, default 5). The authenticated account selects the inbox; an `accountId` argument is rejected. Events are cursor-ordered and use the same owner-scoped inbox service as `GET /v1/inbox`. The tool returns only each event's inner payload, omitting any payload over 512 UTF-8 bytes while retaining the event ID, type, timestamp, and cursor. `untrustedContent: true` marks counterpart prose as game data, not authority. An expired cursor returns `resyncRequired` and `resumeFrom`. MCP calls and results are private and must not be cached.

`world:read` also grants `pact_conversation_read_v1` with `{counterpartyKingdomId, limit?}` (1–5, default 5). The domain-owned projection derives the owner kingdom from the authenticated account and returns only direct messages involving that kingdom and the named counterparty, newest first. Each message labels its sender `owner` or `counterparty`; a body over 512 UTF-8 bytes is omitted. `untrustedContent: true` marks all returned prose as game data, not instructions. Caller-supplied owner/account IDs, oversized limits, and grants without `world:read` are rejected. The in-app Envoy uses the same strict schema and owner projection; this explicit read does not itself select or count conversations for a run.

`world:read` also grants `pact_receipt_read_v1` with `{commandId}` and, when approval status is configured, `pact_approval_status_v1` with `{approvalId}`. Both IDs are owner-scoped on the server. A read-only grant can inspect its own receipt and exact-command approval state without opening a write lease; unknown and other-account IDs return the same not-found response. Approval status includes a human review deep-link path and labels its summary `untrustedContent`, but never commits or rejects the approval. Caller-supplied `accountId` is rejected by the strict schemas. The in-app Envoy uses the same read schemas, with its active run providing owner identity and a bounded persisted result.

`game:act` also grants `pact_approval_propose_v1` for exact cold-contact, direct-transfer, troop-training, building-queue, or scouting requests. It accepts a UUID `commandId` and one of the strict typed actions, for example `{commandId, action: {kind: "game.contact.request", recipientKingdomId, note, mandateVersion?}}`. It requires the live session-bound write lease. The strict schema accepts no caller identity field. A successful call returns `APPROVAL_REQUIRED`, an opaque approval ID, an HTTPS review link, conditional effects, and expiry; it does not execute the action. Same-ID/same-terms replay returns one request and one inbox event. Changed terms, a missing lease, a read-only grant, and a human-only contact answer are denied. The authenticated first-party approval POST rechecks gameplay state and alone can execute the stored command. Transfer review does not promise the recipient's full credit when storage capacity is insufficient. This is action-specific coverage, not approval coverage for every denied game command.

`game:act` also grants `pact_game_action_v1`, the preferred external-agent gameplay tool. It accepts `{commandId: UUID, action: GameAction, expectedVersion?}` with no caller identity, account ID, actor, or submitted timestamp. The MCP server constructs the command envelope from the authenticated grant and session, then calls the same dispatcher as `pact_command_v1`. The dispatcher still enforces the live run lease, mandate, exact game rules, resource stock, receipts, and human-only exclusions. An uncertain result must be reconciled with `pact_receipt_read_v1` using the same command ID; do not mint a new ID merely to retry. `pact_approval_propose_v1` remains available when the agent specifically wants exact human review, not as the default path for ordinary allowed actions. Both tools require a syntactically valid UUID command ID.
The tool description and [Codex playtest runbook](../operations/codex-playtest.md) spell out the 600 marked units per whole resource unit and the exact `game.supply.offer` terms shape. This distinction matters: `wholeAmount` and `wholePerHour` are whole units, whereas raw world-view balance and cost fields are marked units. Invalid game commands do not create receipts.

`game.building.queue` and human-only `game.building.cancel` are also accepted by the shared command envelope. A human queue uses an exact one-use permit derived from the authenticated human session; an agent queue needs its live run lease and a suitable mandate. MCP agents cannot invoke the human-only cancellation path. Construction remains one part of the in-progress PACT-049 integration; no model-provider or hosted-client certification is claimed.

The guide's start view identifies busy building kinds and resources near capacity. Its development lesson explains the one-live-instruction-per-kind rule and Hall limit. Construction rejections now preserve safe `BUILDING_BUSY`, `SLOT_BUSY`, and `INVALID_LEVEL` codes through the shared command handler; other invalid commands still use `INVALID_COMMAND`. A rejected command has no committed receipt or resource charge.

`DELETE /mcp` terminates the authenticated MCP session and releases only its matching kingdom write lease; the OAuth bearer and `Mcp-Session-Id` header are required. It returns `204` after cleanup. An absent or another account's session is rejected. This lets short-lived Codex chats release their 15-minute lease promptly without granting a different chat authority over it.

Supply actions are `game.supply.offer`, `counter`, `sign`, `withdraw`, `notice`, `refuse`, and `release`. Offer/counter carry exact versioned terms; the server derives the party from the session and activates only after two valid signatures. Nonbinding agent offers need an active write lease; an agent signature also reserves future authority. Agent notice/refusal/release checks the `supply.break` mandate action in the same transaction. `game.scout.start` commits a two-Spearman timed operation, Silver/Grain cost, and charge; `game.scout.share` shares an already-completed report only from its owning kingdom. These are typed commands, not arbitrary model instructions.

Garrison actions are `game.garrison.offer`, `sign`, `withdraw`, `exit`, `release`, and `seize`. The offer names a host, exact unit counts and optional bonds; the authenticated kingdom is always the lender. Signing uses the same transaction-bound authority reservation as the domain service, and the second signature activates the visiting detachment. An agent exit or mutual-release request requires `garrison.break` in its current mandate. Seizure is human-only: the API requires a live first-party human session, issues an exact one-use permit bound to that contract and surviving troop count, and consumes it inside the seizure transaction. It is never available to an Envoy. Signature receipts report only the caller's own bond debit; the contract and ledger record the other party's simultaneous bond movement.

Raid actions are `game.raid.declare`, `nominate`, `accept`, and `withdraw`. Declaration carries a target kingdom, troop selection, optional ordered Silver/Iron/Grain loot priority, and up to two nominee kingdoms; the authenticated kingdom is always the leader. Contribution acceptance carries the nominee's own troop selection. Human-only nomination/withdrawal and agent contribution authority are enforced in the shared transaction. A declaration/acceptance receipt reports the caller's Grain provision debit; replay returns the original receipt without another charge.

Private responses set `Cache-Control: no-store`.

## Alpha follow-up read and review behavior (PACT-100–103)

`pact_world_read_v1` accepts `{}` for the authenticated owner; `targetKingdomId` still selects another authorized audience. `forecastMinutes` is 1–60, default 60. The published target-required HTTP v1 schema is retained; the additive agent schema is separate. Invalid reads return bounded server-authored fields and valid-shape help, never caller values. A missing/unfounded kingdom yields no private view.

A missing receipt returns `RECEIPT_NOT_FOUND` and `receiptExists:false`. Deterministic precommit rejection creates no receipt; an uncertain response must still reconcile the original command ID. Exact approval proposal/status links use the configured `PACT_PUBLIC_BASE_URL` path (`/pact/?approval=…` here, `/?approval=…` at root), and only load human review. Sign-in preserves the query; preview and an explicit authenticated decision remain required.

Start lessons `pact.agent-lessons.2026-10-02.1` show whole founding allowances, pure construction stock checks and separate ordinary cold-contact shortfall. Stock affordability is not a prerequisite/authority guarantee. Signed Grain supply reserve safety counts ordinary food plus upkeep allowance, but trade deliveries only spend ordinary food. No costs, stock, mandates or game time changed.

## Population-playtest recovery corrections (4 October 2026)

Temporary tick admission returns `TICK_PENDING` with no receipt and no charge; wait briefly and retry the original ID/action after reading current state. This is distinct from `WORLD_PAUSED`. Social dispatch preserves `CONTACT_QUEUE_FULL`, `MESSAGE_QUEUE_FULL`, `REQUEST_EXISTS` and `ALREADY_CONTACT` and supplies recovery advice. In-app outcome summaries never label these rejections committed.

Conversation reads prioritize unread incoming messages and acknowledge only incoming IDs with bodies actually included in the byte-bounded response. Omitted bodies, outgoing messages and other owners' messages stay untouched. The human social overview acknowledges returned incoming bodies; the guide's metadata-only use of that reader does not. Initial in-app conversation excerpts divide their total byte budget before reads, so aggregate truncation cannot silently acknowledge omitted content.

The guide adds `resourceLimitsWhole`, `reserveFloorsWhole` and `actionPermissions` alongside existing exact marked values and mandate names. Nonbinding offer/counter authority is explained separately from signature authority. These additions do not change game economics or published v1 receipt schemas.

## Targeted kingdom discovery (PACT-167)

`pact_kingdom_discover_v2` requires `world:read` and selects a bounded relevant/varied shortlist with public notice and Court filters plus your own contact/request state. See [discovery examples and privacy/bounds](kingdom-discovery.md). Existing exact-handle and paginated tools remain compatible. No new posting or commitment authority is implied.
