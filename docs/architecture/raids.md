# Raid lifecycle and operations

`RaidService` in `@pact/kingdom` owns migration `0031_raids.sql`: declarations, two nomination slots, committed contributions, pinned wall, and participant/public reports. It runs only inside the caller's gameplay transaction. `RaidRandomnessService` stores the encrypted seed separately in `0028_raid_randomness.sql`, and the pure `calculateCombat` function determines exact outcomes. The rules worker calls `lockDue` after building/training completion in `boundaries_and_completions`, then `resolveDue` after upkeep/defaults in `battle_and_scouts`, before scout completion. No model or network call occurs inside a raid transaction.

A leader selects a known non-self target, at least eight ordinary troops, optional two named contributors, and a complete loot priority (default Silver → Iron → Grain). Admission assigns the actual UUIDs into one attacking placement, spends one raid charge and 5 Grain plus two hours of normal upkeep as ordinary Grain, and publishes the seed commitment and target notice. An agent additionally reserves troop/resource authority under `raid.commit`, consumes the provision exposure immediately, and holds the troop commitment until withdrawal/resolution. A nominee accepts and pays its own charge/provisions before lock; an unaccepted invitation spends nothing. A player may have only one active attack as leader or contributor. Before the lock, the leader can cancel the raid and contributors can withdraw; provisions and charges are not refunded. Cancellation reveals the committed seed. The resolution deadline is the strictly next minute boundary plus twenty minutes; the lock is five minutes earlier. Commands at the lock timestamp cannot withdraw or join.

At lock, `TroopService.captureBattleEligibility` pins attacker and home/visiting defender IDs, and the raid pins the current wall level. The same defender ID may be in overlapping defensive snapshots without creating a second unit. Pending garrison exits are excluded from new snapshots. At resolution, raids are ordered by deadline then declaration sequence. Each battle reads only surviving snapshot IDs, so earlier casualties (and starvation deaths) disappear from later battles. Hunger and ordinary target stock are sampled then. The deterministic seed is revealed, the pure calculator produces casualties/loot, the ledger removes only ordinary target stock and credits the leader subject to storage cap, and surviving attackers return home in one transaction. Pending garrison returns finish after battles, then scouts sample the post-battle state. The participant report contains inputs and exact trace; the public report contains identities, time, winner, and revealed seed, but no military amounts or private stock.

The API and rules worker require the same stable 32-byte `RAID_SEED_ENCRYPTION_KEY_BASE64`; development API instances without it reject raid commands. For local use, generate it privately with `openssl rand -base64 32` and inject it as an environment variable. The single-VPS deployment script generates `/srv/pact/secrets/connection-test/raid_seed_encryption_key` (or the configured `PACT_SECRETS_DIR` equivalent) once if absent; Compose mounts it into the API and rules processes. Preserve this secret with database backups or unresolved raids cannot be decrypted after restore. Rotating it needs an explicit seed re-encryption migration; never replace it casually. Completed/canceled raids and reports are exported to their participants and purged after 180 real days, alongside seed evidence. Run `npm run db:migrate` before restarting the worker.

PACT-049 adds authenticated public command/approval routing and authorized read projections. Until then, `RaidService` is an application-layer rules dependency, not a direct client endpoint.
