# Transaction and recovery verification

PACT-051 is in progress. Run the deterministic database suite with `npm run test:integration` on Node 24 and PostgreSQL 17. The seeded scenario in `tests/integration/rules-adversarial.test.ts` uses seed `0x51c0ffee` for 120 ledger operations. Each successful operation is retried under the same idempotency key; every eleventh eligible operation first throws before commit. After each step, it compares committed ordinary, locked, and restricted balances to an independent state model, then reconciles the final balances to the movement journal. A failed transaction must leave no movement.

The same fixture launches a separate Node process using the ledger package and kills it with `SIGKILL` before and after a database commit. The pre-commit movement must roll back with zero stock; the post-commit movement and stock must remain, and retrying its operation key must not add a second movement. This tests an application writer process boundary against the local PostgreSQL server, not death of the durable inference worker or a full VPS outage.

`tests/integration/run-process-death.test.ts` starts separate inference executors with synthetic providers. One is blocked after durable request reservation; another commits a game message through the production game dispatcher and is then killed before run-step reconciliation. After each job lease expires, a replacement claimant runs the same conservative redelivery branch as the worker. The run fails ambiguously, clears reserved tokens, releases its write lease, and finishes the job without a second provider request or fabricated tool result. In the post-command case one owner-authored message, its command receipt, and its outgoing-message charge survive. The fixture needs built workspace packages and the inference worker (`npm run build`) plus a disposable PostgreSQL 17 test database. It does not test a live provider or full VPS restore.

Run `npm run build:packages` then `node scripts/rehearse-rules-restore.mjs` to exercise a separate temporary database schema. The script writes a synthetic kingdom, stock movement, troop, command receipt, and outbox event; uses `pg_dump` and `psql` to restore that schema; compares recovered balances to movement sums and troop placement to the pre-dump identity; then claims and delivers the outbox event twice to prove consumer deduplication. It drops only its temporary schema in cleanup. It requires PostgreSQL client tools compatible with the server and `TEST_DATABASE_URL` pointing at a disposable test database. Never run it against a production database. A schema-level restore verifies these records, not the full single-VPS backup/WAL runbook.

Existing focused fixtures cover clock rollback and lease fencing (`world-clock.test.ts`), grant/provenance/overflow and concurrent overspend (`resource-ledger.test.ts`), authority reservations (`authority-exposure.test.ts`), exact 360 supply installments and defaults (`supply-settlement.test.ts`), troop ownership and locks (`troops.test.ts`), overlapping raid order and resolution rollback/retry (`raids.test.ts`), combat/dice fixtures (`packages/domain/src/combat.test.ts` and `raid-randomness.test.ts`), account closing (`retirement.test.ts`), and receipt/outbox rollback (`persistence.test.ts`). The overlapping-raid fault fixture raises after both battles are processed but before commit, then verifies unchanged troop placement, stock, raid status, and zero resolution events; retry commits exactly two reports/events and a further retry changes nothing. `runs.test.ts` additionally exercises the Version 1 start ceiling: over-limit calls, tokens, duration, selected conversations, and messages, plus invalid numeric inputs, leave no run, write lease, or inference job. Exact maxima remain valid. This is admission evidence for R06, not a provider-billing guarantee.

The `world-clock.test.ts` serialization fixture waits for `next_tick_due_at <= clock_timestamp()` rather than assuming a host timer crossed the database's due time. It still holds a command transaction across tick admission and verifies publication waits for that command before the next sequence is visible.

The retirement retention fixture uses a synthetic September 2026 clock, whereas PostgreSQL stamps movements, raid closure, and retirement with its real wall clock. The fixture explicitly aligns those synthetic history timestamps before advancing 181 days. This keeps the 180-day boundary reproducible after the real test date moves beyond the fixture date; it does not change production timestamp behavior.
