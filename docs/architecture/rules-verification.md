# Transaction and recovery verification

PACT-051 is in progress. Run the deterministic database suite with `npm run test:integration` on Node 24 and PostgreSQL 17. The seeded scenario in `tests/integration/rules-adversarial.test.ts` uses seed `0x51c0ffee` for 120 ledger operations. Each successful operation is retried under the same idempotency key; every eleventh eligible operation first throws before commit. After each step, it compares committed ordinary, locked, and restricted balances to an independent state model, then reconciles the final balances to the movement journal. A failed transaction must leave no movement.

The same fixture launches a separate Node process using the ledger package and kills it with `SIGKILL` before and after a database commit. The pre-commit movement must roll back with zero stock; the post-commit movement and stock must remain, and retrying its operation key must not add a second movement. This tests an application writer process boundary against the local PostgreSQL server, not death of the durable inference worker or a full VPS outage.

`tests/integration/run-process-death.test.ts` starts separate inference executors with synthetic providers. One is blocked after durable request reservation; another commits a game message through the production game dispatcher and is then killed before run-step reconciliation. After each job lease expires, a replacement claimant runs the same conservative redelivery branch as the worker. The run fails ambiguously, clears reserved tokens, releases its write lease, and finishes the job without a second provider request or fabricated tool result. In the post-command case one owner-authored message, its command receipt, and its outgoing-message charge survive. The fixture needs built workspace packages and the inference worker (`npm run build`) plus a disposable PostgreSQL 17 test database. It does not test a live provider or full VPS game-state restore.

Run `npm run build:packages` then `node scripts/rehearse-rules-restore.mjs` to exercise a separate temporary database schema. The script writes a synthetic kingdom, stock movement, troop, command receipt, and outbox event; uses `pg_dump` and `psql` to restore that schema; compares recovered balances to movement sums and troop placement to the pre-dump identity; then claims and delivers the outbox event twice to prove consumer deduplication. It drops only its temporary schema in cleanup. It requires PostgreSQL client tools compatible with the server and `TEST_DATABASE_URL` pointing at a disposable test database. Never run it against a production database. A schema-level restore verifies these records, not the full single-VPS backup/WAL runbook.

Existing focused fixtures cover clock rollback and lease fencing (`world-clock.test.ts`), grant/provenance/overflow and concurrent overspend (`resource-ledger.test.ts`), authority reservations (`authority-exposure.test.ts`), exact 360 supply installments and defaults (`supply-settlement.test.ts`), troop ownership and locks (`troops.test.ts`), overlapping raid order and resolution rollback/retry (`raids.test.ts`), combat/dice fixtures (`packages/domain/src/combat.test.ts` and `raid-randomness.test.ts`), account closing (`retirement.test.ts`), and receipt/outbox rollback (`persistence.test.ts`). The overlapping-raid fault fixture raises after both battles are processed but before commit, then verifies unchanged troop placement, stock, raid status, and zero resolution events; retry commits exactly two reports/events and a further retry changes nothing. The matrix below maps those fixtures to release criteria and identifies the missing verification.

The single-VPS `infra/production/bin/restore-drill.sh` verifies `pg_basebackup`'s manifest/WAL, boots Restic-restored PostgreSQL 17 in a disposable, network-isolated container, reconciles game balances with the movement journal, and persists/retries a synthetic outbox delivery only in that recovered copy. After release `mvp-20260926-1`, snapshot `2ba99a33` (26 September 2026) additionally passed the optional synthetic fixture checks: one activated kingdom, eight home guards at home, one Farm II building instruction, and one committed command receipt. This establishes a representative physical gameplay-state recovery; it does not close the generated all-command R06 fault matrix.

The PACT-049 route matrix also submits every currently human-only game action through the in-app fake-provider tool and an MCP lease with forged human/other-account actor fields. Contact answer, training cancel, troop disband, building cancel, garrison seize, raid nominate, and raid withdraw all fail without a committed receipt or exact human permit. A separate contract fixture checks the 28 published game action kinds against web, MCP, and model schemas. This establishes those privilege/schema boundaries, not behavioral equivalence for all permitted actions.

The cold-contact proposal fixture adds a narrow R04/R06 bridge: fake-model and MCP agent requests are lease-bound and create one owner approval event without spending stock; only a human-authenticated HTTP POST commits the exact contact request and two-Silver debit. Replay and changed-term denial are explicit. A paused dispatcher returns a noncommitting receipt and leaves the approval pending. This does not replace the generated transition matrix or single-VPS base/WAL recovery rehearsal.

`mcp-approval-inbox.test.ts` also holds a sandbox approval dispatch between admission and receipt persistence while the same human attempts rejection and duplicate approval. The approval row lock spans that interval: the command has one receipt, the duplicate approval sees it, the rejection fails as already resolved, and exactly one approved inbox/outbox resolution exists. Separate expired approve and reject attempts persist `expired` before returning the error. This is one approval-state race and expiry fixture, not exhaustive all-command fault injection.

`runs.test.ts` additionally exercises the Version 1 start ceiling: over-limit calls, tokens, duration, selected conversations, and messages, plus invalid numeric inputs, leave no run, write lease, or inference job. Exact maxima remain valid. This is admission evidence for R06, not a provider-billing guarantee.

The `world-clock.test.ts` serialization fixture waits for `next_tick_due_at <= clock_timestamp()` rather than assuming a host timer crossed the database's due time. It still holds a command transaction across tick admission and verifies publication waits for that command before the next sequence is visible.

The full-phase clock fixture records each of the nine tick phases in a temporary PostgreSQL table. Each handler verifies that all and only preceding phases are visible inside the same transaction. A paused clock writes no trace or tick; resume advances one game minute and publishes one tick and outbox event; a duplicate advance leaves one trace. This verifies clock orchestration and atomic visibility, but the handlers are synthetic and do not yet prove the combined harvest/contract/battle/scout domain effects required by R02.

The retirement retention fixture uses a synthetic September 2026 clock, whereas PostgreSQL stamps movements, raid closure, and retirement with its real wall clock. The fixture explicitly aligns those synthetic history timestamps before advancing 181 days. This keeps the 180-day boundary reproducible after the real test date moves beyond the fixture date; it does not change production timestamp behavior.
