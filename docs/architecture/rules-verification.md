# Transaction and recovery verification

PACT-051 is in progress. Run the deterministic database suite with `npm run test:integration` on Node 24 and PostgreSQL 17. The seeded scenario in `tests/integration/rules-adversarial.test.ts` uses seed `0x51c0ffee` for 120 ledger operations. Each successful operation is retried under the same idempotency key; every eleventh eligible operation first throws before commit. After each step, it compares committed ordinary, locked, and restricted balances to an independent state model, then reconciles the final balances to the movement journal. A failed transaction must leave no movement.

The same fixture launches a separate Node process using the ledger package and kills it with `SIGKILL` before and after a database commit. The pre-commit movement must roll back with zero stock; the post-commit movement and stock must remain, and retrying its operation key must not add a second movement. This tests an application writer process boundary against the local PostgreSQL server, not death of the durable inference worker or a full VPS outage.

`tests/integration/run-process-death.test.ts` also starts a separate inference executor with a synthetic provider blocked after durable request reservation. The test kills that process, waits for its durable-job lease to expire, and has a replacement claimant run the same redelivery recovery branch as the worker. The run must fail ambiguously, clear reserved tokens, release its write lease, and finish the job without a second provider request or a fabricated tool result. The fixture needs built workspace packages (`npm run build:packages`) and a disposable PostgreSQL 17 test database. It does not test a live provider, process death after a game-command commit, or a full VPS restore.

Run `npm run build:packages` then `node scripts/rehearse-rules-restore.mjs` to exercise a separate temporary database schema. The script writes a synthetic kingdom, stock movement, troop, command receipt, and outbox event; uses `pg_dump` and `psql` to restore that schema; compares recovered balances to movement sums and troop placement to the pre-dump identity; then claims and delivers the outbox event twice to prove consumer deduplication. It drops only its temporary schema in cleanup. It requires PostgreSQL client tools compatible with the server and `TEST_DATABASE_URL` pointing at a disposable test database. Never run it against a production database. A schema-level restore verifies these records, not the full single-VPS backup/WAL runbook.

Existing focused fixtures cover clock rollback and lease fencing (`world-clock.test.ts`), grant/provenance/overflow and concurrent overspend (`resource-ledger.test.ts`), authority reservations (`authority-exposure.test.ts`), exact 360 supply installments and defaults (`supply-settlement.test.ts`), troop ownership and locks (`troops.test.ts`), overlapping raid order and resolution rollback/retry (`raids.test.ts`), combat/dice fixtures (`packages/domain/src/combat.test.ts` and `raid-randomness.test.ts`), account closing (`retirement.test.ts`), and receipt/outbox rollback (`persistence.test.ts`). The overlapping-raid fault fixture raises after both battles are processed but before commit, then verifies unchanged troop placement, stock, raid status, and zero resolution events; retry commits exactly two reports/events and a further retry changes nothing. The retirement retention fixture uses a synthetic September 2026 clock, whereas PostgreSQL stamps movements, raid closure, and retirement with its real wall clock. The fixture explicitly aligns those synthetic history timestamps before advancing 181 days. This keeps the 180-day boundary reproducible after the real test date moves beyond the fixture date; it does not change production timestamp behavior.
