## Live playtest, 26 September

Two synthetic accounts were created and verified through the deployed captured-email flow without recording a token. Aster Vale was founded in the in-app browser; Briar Keep was founded through the public API as the second player. The browser committed a Farm II construction order and showed the allowance decrease and occupied builder slot. Immediate training and contact attempts were rejected because ordinary resources started at zero; the client had incorrectly displayed both as `INVALID_RESPONSE`. The SDK now reads the top-level code from non-2xx game receipts, so `INSUFFICIENT_STOCK` is visible. A kingdom ID is now displayed in the header, and the UI offers re-sign-in for a new tab's CSRF token.

After ordinary Silver accrued, Aster Vale's contact request committed with a 2 Silver charge (1,200 internal units at 600 units per resource); Briar Keep accepted it, then sent a message, all through the public API. Both `/v1/inbox` reads returned no social item. Graph tracing found no application caller of `SocialService.listMessages`; the existing inbox is an Envoy event stream, not the social read path. This means the web UI could not then discover a pending contact, read the received message, or share offer IDs in-game. Switching away from People also cleared the manually entered target ID. A browser `window.confirm` during a supply-offer attempt stalled the in-app browser automation; no offer result is claimed. This playtest does **not** satisfy the two-player UI acceptance or establish that raids/trade/report flow is playable.

Qualitative verdict: founding and the first build provide a brief sense of progress, but the current Alpha is not yet fun to play with a friend. The first-session resource wait, UUID entry, raw JSON profile, and invisible social loop turn play into an operator exercise. The next work should expose authorized contact/message/offer reads and exact IDs in the UI, then repeat the complete two-player browser sequence before marking PACT-048 done.

## Chrome desktop iteration, 26 September

Release `alpha-20260926-4` adds an owner-only `GET /v1/game/social` read, visible contacts, pending requests, bounded messages, open offers and signed contracts, direct exact-version signing, persistent target selection across tabs, and inline gameplay confirmations. Resource displays now use the specified 600 internal units per resource. The earlier 1.2 Silver contact-fee interpretation above was a display error: 1,200 internal units is **2 Silver**. The desktop layout was widened and card/section hierarchy improved. The social read requires a human session, derives the kingdom from the account, refuses bearer-only access, and sends `no-store`. The owner route test verifies these boundaries.
