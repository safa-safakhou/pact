# Authentication persistence review — 10 October 2026

The founder requested inspection of authentication and persistence, clarifying that persistence must cover both the same browser and other devices. This is a review and implementation proposal; no authentication code, hosted configuration, player identity or continuous-run settings changed.

## Current behavior

- Live `pact.tinyagenttools.com` has guest play enabled. `GET /v1/play` returned 200 with `enabled: true, guest: false` for an anonymous request. The registration-status endpoint also returned 200 with `registrationEnabled: true`; this boolean does not certify real email delivery or production readiness.
- A guest receives a random UUID entry key stored as `pact_guest_entry` in browser localStorage. The nickname is presentation, not authentication. `IdentityService.joinGuest` HMACs the key and resolves the same account on repeated joins. The key is a bearer recovery credential: possession can obtain a new human session for that guest.
- Both guest and password login set `pact_session` as a Secure, HttpOnly, SameSite=Lax, host-only cookie, with a 30-day lifetime. Server-side sessions have seven-day sliding idle expiry and a fixed 30-day absolute expiry. GuestEntry automatically rejoins with the stored entry key after authentication fails, recovering the same kingdom even after the session expires.
- Guest bootstrap at `/v1/play` restores the session's CSRF token, so a new tab/browser restart can restore write access. The generic password-login path stores its CSRF token only in sessionStorage and has no equivalent generic session-bootstrap endpoint in the inspected routes. Static tracing identifies a gap: a returning password user can have a valid persistent cookie but no CSRF token in a fresh tab, leaving writes disabled or denied. This particular fresh-tab failure was not reproduced in a live browser.
- Email/password login, verification, reset, reauthentication, MFA and revocation exist in the backend. However, guest mode routes login/draft screens to GuestEntry. No guest-to-verified-account conversion or portable guest recovery flow was found in the inspected identity/client implementation.
- MCP connections are separate OAuth grants: 15-minute access tokens and rotating 30-day refresh tokens, with reuse detection. Web login persistence does not replace these grants. Existing logical MCP sessions reconnect within the authenticated grant, rather than starting a fresh write lease on every transport reconnect.

Browser storage belongs to an origin; localStorage survives browser sessions, while sessionStorage belongs to a page session and is cleared when that session ends. Private browsing/storage clearing can erase guest recovery. Moving to another device, browser profile or domain does not automatically carry the entry key. See [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) and [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).

## Hosted persistence evidence

Read-only inspection of `root@2.31.62.91` found API image `pact-runtime:social-repair-20261009-1`, guest setting `PACT_GUEST_PLAY=1`, and PostgreSQL 17.11 with the named `pact-production_postgres-data` volume. Identity pepper and encryption-key files are bind-mounted into the API. Ordinary application-container replacement therefore has persistent database/secret backing; rotating or losing the pepper invalidates token/key lookups. Actual server/browser restart was not performed, and host-loss recovery was not rehearsed in this review. Preserve the database volume and secret files together; the existing backup design's same-host limitation remains.

An initial Python request using its default user agent received an HTTP error. Retrying with a browser-style user agent returned the successful public results above; internal API reads also returned the same results. This was not evidence of an authentication outage.

## Proposed implementation, in order

1. Add a generic cookie-authenticated session bootstrap that returns safe account/session metadata and restores CSRF for guest and registered accounts. Restore it before enabling writes. Use a stable session-bound CSRF mechanism so parallel tabs do not invalidate one another. Keep session bearer tokens in HttpOnly cookies and retain expiry, origin checks and explicit sensitive-action reauthentication.
2. Add **Save your kingdom** while the guest owner is authenticated: set an email/password and verify email, converting the existing account in place. Do not create a second kingdom or reassign game ownership. Preserve the same account ID, kingdom, history and OAuth grants. Define conflicts with already-registered email addresses explicitly; do not silently merge accounts. Remove/revoke the old guest recovery capability on completed conversion, and use recent verified authentication for authority/security changes thereafter.
3. Expose **Sign in to an existing kingdom** alongside guest entry. A second device signs in with verified credentials and receives its own session for the same account. Provide working verification/reset delivery and clear session-expiry recovery. The registration gate alone is insufficient evidence that outbound email works; validate the actual delivery route before advertising recovery.
4. Verify same-browser close/reopen, independent new tabs, expired sessions, second-device login, original kingdom/grant preservation, failed verification, duplicate email, reset/revocation, cross-account isolation and CSRF. Keep the current seven-idle/30-absolute policy unless a separately documented policy change is requested.

A short-lived, single-use owner-authorized device-pairing code could be an optional guest-only alternative. It would allow transferring access while the original browser is available, but would not solve recovery after losing all devices. Verified account conversion is the proposed durable solution for both requirements. None of these proposals is implemented by this review.
