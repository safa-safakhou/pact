# PACT-147 — Recovery and device controls

Guest recovery remains immediate and email remains optional. A signed-in human proves possession of the current private recovery code to replace it. The browser privately persists the exact current/new-code intent before sending; the server changes the hash atomically and allows only that same owner's exact retry after a lost response. Revoked old codes fail even on the founding route, preventing a replacement kingdom. Rotation does not change ownership, kingdom or agent grants. Codes are absent from URLs and operational/security events; the replacement is displayed only in Account.

Account also lists active human sessions with current-device identification, last observation and expiry, and lets the owner revoke one session without signing out other devices or revoking agent grants. Writes require the authenticated owner's cookie, Origin and CSRF. Foreign session IDs cannot revoke another owner. Existing seven-day idle/30-day absolute expiry, logout and registered sign-in remain authoritative.

Migration 0057 stores revoked digests with cascading account erasure. Synthetic HTTP/integration checks cover old/new-code refusal/restoration, exact replay and wrong-owner/CSRF denial, preservation of owner/kingdom/account count, independent cookie sessions, current/other/foreign session revocation, and existing expiry/logout/conversion tests. Full regression passes at the communication checkpoint: 326 unit and 343 integration tests, one optional integration skip; full build, types and lint pass.

Actual browser acceptance on an isolated local schema restored the same synthetic owner and kingdom after reload and in a second fresh tab. Account showed the private recovery code hidden by default, the current device, observation/expiry, individual-session revocation and explicit captured-mail status. The test server runs API/rules/web only, with no inference. Recovery rotation and lost-response replay were exercised through the synthetic authenticated HTTP fixtures, without recording browser credentials. A second physical device and a full browser-process shutdown/restart were not observed; those platform-specific certifications remain limitations rather than asserted results. The implementation acceptance uses the observed browser and independent-session evidence; physical-device evidence is unavailable.

Passkeys are an optional future login method: their account binding, authenticator registration/revocation, cross-device and fallback recovery require explicit UX and WebAuthn acceptance. No passkey registration is activated or claimed. Captured SMTP is truthfully identified in Account; existing verification/reset workers provide the transactional adapter, but the operator has not configured a real sender/domain. Real inbox delivery cannot be certified from captured mail. Guest recovery does not depend on that configuration.

The optional recovery/session implementation is complete. Missing real sender, physical-device certification and full browser-process restart remain explicit external acceptance gaps. Neither email delivery nor passkey compatibility is certified by this release.
