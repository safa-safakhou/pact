# Communication diagnosis — PACT-139 follow-up, 9 October 2026

The founder asked why players were not communicating and whether incentives were too low. This is a read-only diagnosis of the finished 25-player comparison and the still-active original 50-player controller. No player run, budget, deadline, mandate or game rule was changed; the finished comparison remains terminal.

## Findings supported by code, logs and database

**The strongest problem is failure to operate the social workflow, with a separate unread-message acknowledgment defect and bottleneck in the original population. Low incentives are a secondary hypothesis, not an established explanation.**

The comparison produced 158 contact-request proposals and thirteen committed requests, but **zero message proposals** across all 553 accepted model plans. None of its requests was accepted. The missing transition is request received → correct recipient's human acceptance → established contact → message/offer → reply/signature. It is not a case of messages being sent and silently lost.

**Correction to the final comparison report:** `continuous.mjs` calls `pact_agent_guide_v1` with topic `start` before every model invocation. `AgentGuideReader.read()` reads the current social overview and includes `contacts`, `contactRequests` with real IDs/directions, and current supply offers/contracts. Incoming contact requests therefore *are* automatically refreshed every turn, subject to prompt paging. The previously stated absence of fresh incoming-request polling was incorrect. What is absent from the automatic start guide is actual direct-message content; selected Council/conversation reads are necessary for that. Extra model-selected reads run after actions and arrive next turn.

A decisive trace involves Gemma's trader, actor 1. It sent request `43376dbc-b74e-47a4-b7c0-04916fc49bb7` to Gemma actor 0, the production builder. Actor 1 then tried `game.contact.answer` with `accept:true` on that same request eleven times (13:11–14:05 UTC). The database confirms actor 0 is the recipient and actor 1 is the sender. Ten attempts returned `INVALID_COMMAND`, one `TICK_PENDING`. This was a **real outgoing request, not a fabricated request ID**. `SocialService.answerRequest` accepts only the recipient owner; trying to approve one's own outgoing request correctly yields `REQUEST_NOT_FOUND`, which is mapped into `INVALID_COMMAND`. The intended recipient never chose the corresponding acceptance command.

Only Gemma proposed any contact answers. Qwen, Granite, Ornith and LFM proposed none. Eight of the thirteen requests targeted Gemma owners, three targeted Ornith owners and two targeted outside the comparison. Four targeted the first Gemma owner, whose production role instead repeated blocked Mine III instructions. This concentrates outreach on recipients who did not respond; equal model roles did not produce matched reciprocal conversations.

There is a **synthetic-controller guidance mismatch**. The ordinary guide correctly says incoming requests require your human and outgoing requests require their human. Its authority lesson says to return a human decision and stop. The experiment's prompt separately says a synthetic owner controller can perform exact human-only actions under founder consent. That controller does not independently decide which contact requests to accept: it only executes actions selected by the model. Thus a model that defers to the guide's human boundary waits indefinitely, while a model that ignores request direction can choose an impossible acceptance. This is plausible contributing confusion; the logs establish wrong-owner selection and no recipient acceptance, not each model's hidden reasoning.

The execution bridge itself contains the correct route: contact answers are agent-forbidden; `dispatchFullCommand` retries that exact authorized synthetic decision through the normal owner command path. Existing targeted tests pass for the `FORBIDDEN` → exact owner command transition and preservation of stock/authority refusals. Nothing in this investigation demonstrates that legitimate recipient acceptance is broken. No production contact was accepted as a diagnostic probe.

## Original 50-player population: conversations are not being serviced

At 15:32 UTC, its journal contained 3,237 accepted plans, **three message proposals**, zero contact-answer proposals and one cold-contact proposal. Its recorded message outcomes were `RUN_ALREADY_ACTIVE`, `MESSAGE_QUEUE_FULL` and `FORBIDDEN`; no successful message receipt appeared in that controller journal. The database has two agent-originated messages from these owners since the continuous start, both at 09:36:25–26 UTC, but these do not match committed message receipts in the journal and must not be credited to this worker without further provenance.

A scoped database snapshot at 15:33:59 UTC found **263 existing contacts within the original cohort**, **201 unread messages across 35 recipients**, and **22 sender/recipient pairs with at least four unread messages**. No recipient reached the separate 48-agent-message aggregate cap. This backlog includes earlier play and is not evidence of 201 new messages from today's continuous controller.

`SocialService.sendMessage` refuses a fifth unread message on a directional pair. Reading through the main Council view or conversation reader acknowledges delivered messages and clears that pressure; simply reading world state or the start guide does not. **The standalone `pact_council_thread_v1` path is inconsistent:** `CouncilReader.thread()` returns message rows and pagination without calling message acknowledgment or updating `read_game_time_ms`. A model can therefore actually read a thread without clearing its unread backpressure. This is a concrete code defect in the thread read path, not just weak model strategy. The original worker requested 3,181 world reads, but zero play-view or conversation reads and only 53 Council-thread reads. Those thread reads do not acknowledge messages in the current implementation, and cannot drain the backlog through that path. The aggregate snapshot does not prove that all 22 blocked pairs were among those 53 reads; the missing acknowledgment is independently established by source inspection. `MESSAGE_QUEUE_FULL` is consequently an actual observed admission failure, not hypothetical infrastructure trouble. Existing contacts remove the introduction barrier for these owners, yet the models scarcely choose messaging at all.

The runner has a single-turn memory, replaces selected read results each turn, and does not maintain a durable conversation agenda or automatically prioritize pending social work. The models can select the necessary tools, but repeatedly focus on construction, offers or unsuccessful signatures. A live scheduler and valid JSON do not provide an autonomous conversation strategy.

## Incentives: what can and cannot be concluded

Cold introductions cost two **ordinary** Silver. Fresh kingdoms start with zero ordinary stock; construction allowances cannot pay that charge. Several early requests therefore correctly failed for stock, then succeeded later. Acceptance has no corresponding Silver debit, and messaging existing contacts has no per-message Silver cost. Once thirteen requests were pending, the sender's cost no longer explains why recipients did not accept them.

Fresh kingdoms share the same starting production and allowances, and construction offers a more immediate visible benefit than waiting for another agent. Trade is optional rather than a compulsory progression step. Those facts make weak relative trade motivation plausible, particularly in a two-hour run. However, roles explicitly included negotiation/diplomacy, models repeatedly *attempted* social actions, and they failed request direction, state recovery and factual grounding. There was no incentive-controlled experiment, so it would be unjustified to declare the game's incentive balance the primary cause or alter the economy on this evidence.

## Recommended repair order

1. Correct `CouncilReader.thread()` to acknowledge only incoming message IDs actually returned in its authorized page, following the shared conversation-reader behavior. Verify recipient-only ownership and idempotent reads, and that reading a blocked pair allows the next message without removing anti-spam caps.
2. For explicitly authorized synthetic owners, provide a concise social work queue before each decision: incoming requests with recipient identity/direction, unread exchanges, outgoing requests awaiting another owner and offers needing this owner. Keep the normal human guide and human-only authority boundaries intact. Make the exact synthetic-owner route explicit and reject trying to accept an outgoing request locally with a useful explanation.
3. Fetch bounded fresh incoming messages as part of normal turn observations, acknowledge only actually delivered/read messages, and retain a conversation agenda and peer/version history across turns. Prioritize responding to existing social work before repeating an introduction. Do not remove message caps or forge acceptance to create activity.
4. Preserve specific authorized denial reasons and require recovery to change the failed plan. Surface `REQUEST_NOT_FOUND`/wrong recipient and queue pressure rather than an undifferentiated failure where safe. Supply factual outcomes so an agent cannot present an uncommitted scout/build as completed.
5. Only after that workflow is verified, evaluate two authorized synthetic peers through request, recipient acceptance, actual messages, counterterms and bilateral activation. Then compare incentives/roles or inference settings under a separately authorized budget. The completed comparison must not be resumed.

These are recommendations; this request was to diagnose and report. No controller, production settings or economy were changed. Eight existing full-game adapter tests passed, including the owner bridge and recovery cases. Read-only cohort queries and journal aggregates support the observations. The report does not claim a new live end-to-end conversation test or an incentive A/B result. Credentials and message bodies remain protected.
